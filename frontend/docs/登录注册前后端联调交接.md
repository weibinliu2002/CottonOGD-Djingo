# 登录注册前后端联调交接

## 当前问题

登录页与普通用户注册页已接入，但通过当前前端代理提交时，登录和注册均收到 HTTP 403。

已做的无凭据检查：

- `POST /CottonOGD_api/api/auth/register/` 与 `POST /CottonOGD_api/api/auth/login/`（空 JSON `{}`）都返回 Django HTML 403，页面内容为“CSRF 验证失败”，而不是 API 约定的 JSON 参数错误。
- `GET /CottonOGD_api/api/auth/methods/` 返回 iCotton 的 `index.html`，不是 API 的 401 JSON。
- 当前 checkout 的 `backend/mysite/urls.py` 将 `/CottonOGD_api/` 挂到 `CottonOGD.urls`；`backend/CottonOGD/urls.py` 目前只有旧的会话 `/login/`、`/logout/`，没有文档中的 `/api/auth/*` 路由。未命中的 SPA fallback 会返回前端页面。

因此当前 403 发生在新登录/注册业务逻辑之前；无法据此判断管理员账号或密码是否正确。请先确认认证 API 已部署到前端实际代理的 Django 服务，并确认路径与 CSRF 处理方式。

## 前端当前约定

当前前端请求路径为：

| 功能 | 请求 |
|---|---|
| 注册普通用户 | `POST /CottonOGD_api/api/auth/register/` |
| 登录 | `POST /CottonOGD_api/api/auth/login/` |
| 获取当前用户 | `GET /CottonOGD_api/api/auth/me/` |
| 刷新 access token | `POST /CottonOGD_api/api/auth/refresh/` |

现有 API 文档写的是 `/api/auth/*`。前端按项目现有 Django 挂载方式，在其前面加了 `/CottonOGD_api`。请后端确认最终对外路径是否确为 `/CottonOGD_api/api/auth/*`；若实际部署在其他前缀，请提供最终路径，不要让前端猜测或改写请求。

成功响应按现有 API 文档使用：

```json
{
  "code": 0,
  "message": "success",
  "data": {
    "access": "...",
    "refresh": "...",
    "user": {
      "id": 1,
      "username": "example",
      "email": "example@example.org",
      "email_verified": true
    }
  }
}
```

注册请求体：

```json
{
  "email": "example@example.org",
  "username": "example",
  "password": "由用户填写",
  "confirm_password": "由用户填写"
}
```

登录请求体只发送一种标识：

```json
{ "email": "example@example.org", "password": "由用户填写" }
```

或：

```json
{ "username": "example", "password": "由用户填写" }
```

错误响应应为 JSON，而不是 Django HTML 页面，例如：

```json
{
  "error": {
    "code": "invalid_param",
    "message": "请输入有效的邮箱地址"
  }
}
```

## 需要后端确认/补齐

1. **挂载路由并部署到前端代理的服务。** 至少需要 `register/`、`login/`、`me/`、`refresh/`；其余接口按 [登录注册与第三方登录 API 文档](./登录注册与第三方登录_API文档.md) 实施。
2. **确认 CSRF 处理。** 这是基于 JSON + Bearer JWT 的 API。建议使用 DRF APIView / `@api_view` 并明确认证类与权限类；公开注册、登录、刷新接口应能到达参数校验并返回 JSON。不要通过全局关闭 Django CSRF 来解决。如果这些接口确实依赖 session/cookie，请提供 CSRF token 初始化接口和前端所需的 cookie/header 契约。
3. **返回管理员角色字段。** 当前 API 文档的 `user` 字段没有管理员标识，但前端需要区分普通用户与后端生成的管理员账号。请在登录响应及 `/me/` 中稳定返回 `is_staff`/`is_superuser`，或统一的 `role: "admin" | "user"`。管理员账号由后端生成，不应开放管理员注册。实际管理 API 仍须在后端做权限校验，前端路由判断仅用于页面分流。
4. **返回明确的 API 状态与错误格式。** 参数错误 400、凭据错误 401、未验证邮箱或限流 403、重复注册 409 等按 API 文档返回 JSON，便于前端显示后端提示。

## 后端验收建议

请在部署到与前端相同的代理目标后验证：

1. `POST /CottonOGD_api/api/auth/register/` 提交 `{}`：返回 400 JSON 参数错误，不能返回 CSRF HTML 403。
2. `POST /CottonOGD_api/api/auth/login/` 提交 `{}`：返回 400 JSON 参数错误；不需要使用真实密码做此检查。
3. `GET /CottonOGD_api/api/auth/methods/` 不带 token：返回 401 JSON，不能返回 SPA HTML。
4. 普通用户完成邮箱验证后登录：返回 access、refresh 和非管理员角色；`/me/` 返回一致的用户资料。
5. 后端生成的管理员账号登录：返回管理员角色；普通用户访问受保护的管理 API 必须被后端拒绝。
6. 使用 refresh token 获取新 access token，并验证过期 access 的刷新流程。

## 前端页面入口

- `/login`：邮箱或用户名登录；根据 `/me/` 返回的角色进入对应页面。
- `/register`：仅普通用户注册；注册成功后提示邮箱验证。
- `/account`：普通用户页。
- `/account/admin`：管理员页。

这些入口暂未加入导航栏。更多字段、验证码邮箱、限流、密码重置及第三方登录约定见 [登录注册与第三方登录 API 文档](./登录注册与第三方登录_API文档.md)。
